### Checkpoint/resume mechanics (from `src/fastwam/trainer.py`)
- `resume=<dir>` restores full accelerate/deepspeed state (optimizer/step/dataloader position) via `trainer_state.json` in `checkpoints/state/step_XXXXXX/`.
- `resume=<file.pt>` only loads weights (`FastWAM.load_checkpoint`, strict=False for mot) — no optimizer/step restore. This is also exactly how LIBERO eval loads `ckpt=`, so the released `libero_uncond_2cam224.pt` is a single consolidated weights-only file usable both ways.
- Only `model.dit` (the combined video+action "mixture of transformers") and optional `proprio_encoder` are trainable by default (`Wan22Trainer._apply_dit_only_train_mode`); VAE and text encoder stay frozen. No LoRA/adapters present in the codebase currently.
- `configs/task/libero_uncond_2cam224_1e-4.yaml`: batch_size 16, lr 1e-4 cosine, 10 epochs, save_every 2000, eval_every 200 steps.
- `scripts/train_zero1.sh <nproc_per_node> [hydra overrides]` — GPU count is NOT hardcoded to 8, fully configurable via first arg (deepspeed ZeRO stage 1, bf16).

### Bug found in `run_libero_parallel_test.sh`'s completion check (2026-08-08)
`run_libero_eval()`'s main loop computes `total_completed=$(find "$OUTPUT_DIR" -type f -name "gpu*_task*_results.json" | wc -l)` and declares `"All tasks are complete!"` (triggering `summarize_results.py` and exiting) once `total_completed -eq total_tasks`. This `find` is **not scoped to the current invocation's task list or suite** — it counts every matching result file anywhere under `$OUTPUT_DIR`, recursively, across all suites. **If the same `output_dir` is reused across two separate `run_libero_manager.py` invocations** (e.g. relaunching just `libero_90` into the same directory that already has 40 completed results from a prior `[spatial,object,goal,10,libero_90]` run), the scheduler can hit its target count using a mix of old + new results and exit **before the current run's own task list is actually done** — even while workers are still legitimately mid-flight. Observed directly: relaunched `libero_90` alone (90 tasks) into an `output_dir` that already had 40 files from the other suites; scheduler declared completion at 51 real `libero_90` results (40 old + 51 new = 91 >= 90 triggered it), while 6 processes were still actively running further tasks and 33 tasks had never been launched at all.
**Workaround used**: let the still-running processes (visible via `ps aux`/`tmux list-panes` — the tmux session itself survives the parent script exiting) finish naturally, then compute the true missing task-ID set directly from the suite's own result directory (`glob` + regex on `gpu*_task*_results.json`, compare against `range(n_tasks)`) rather than trusting the scheduler's own "complete" declaration, and launch a fresh manager/task-file run scoped to exactly the missing IDs once GPU capacity is free. **General lesson: never reuse the same `output_dir` across separate `run_libero_manager.py` invocations for the same suite unless you want this false-completion risk; use a fresh output_dir per invocation and merge/summarize across them afterward, or always verify actual per-suite result counts rather than trusting the scheduler's own completion message.**

### Disk-full crash during exp0003 training (2026-08-09)
Training for exp0003 crashed at the step_004000 checkpoint save (`RuntimeError: ... file write failed`, `unexpected pos ... vs ...` — a truncated-write error from `torch.save`/DeepSpeed's zero-checkpoint writer) because **disk hit 100% full (1016G/1016G)**. Root cause: unlike exp0001/exp0002, I did not clean up superseded `checkpoints/state/step_*` dirs *during* this run, only planned to at the end — with `save_every=500` and `max_steps=4000`, 8 full-state ZeRO-1 checkpoints accumulated (~80GB each, ~640GB total) on top of the pre-existing ~325GB already on disk from prior experiments/data, exceeding the 1016GB volume.
- **Recovery**: the *weights-only* `.pt` checkpoint (`step_004000.pt`, ~12GB) had already been written successfully before the crash (`save_checkpoint()` writes weights first, full deepspeed state second — see `trainer.py:583-599`) and verified to load correctly (`torch.load(..., weights_only=False)` → valid 1649-key `mot` state dict, `step: 4000`). Only the *resumable* full-state checkpoint for step 4000 was lost/corrupted (the step_003500 state dir remained intact and usable if a resume-from-4000-equivalent was needed, which it wasn't since training had reached its planned max_steps). No compute was wasted — the training itself had already run the intended 4000 steps; only the redundant resume-capability artifact for the final step was lost.
- **Lesson reinforced (this is the *second* time disk cleanup was missed — see also the 79%/80% disk warnings during exp0001/exp0002)**: deleting superseded `state/` dirs must happen proactively *during* a run (e.g. immediately after each new save point is confirmed complete, not just "at the end") for any run with `save_every` frequent enough to produce multiple ~80GB state saves before I next check in. A `df -h` check should be part of every periodic progress-check / GPU-health check during training, not just something done after completion.

### Methodological warning: single-run/n=5-trial weight-tuning comparisons are too noisy (2026-08-09)

After three consecutive data-reweighting experiments (0003: goal/long 5x/5x, 0004: 5x/10x, 0005: 7x/10x), all evaluated on the identical 21-task widened panel at 5 trials/task, the result pattern stopped being interpretable as a clean dose-response to the weight changes:
- **LIBERO-Object regressed from a perfect 100% (0003, 0004) to 85% (0005) despite its own oversampling weight never being touched across any of the three experiments.** This alone demonstrates that suite-level outcomes vary substantially between training runs for reasons unrelated to the specific mix-weight design being tested.
- **The "Goal regression = proportional dilution" hypothesis from 0004 was directly tested and not confirmed in 0005**: Goal's weight was raised to a share (~25.9%) exceeding 0003's working level (~24.3%), yet Goal stayed near 0004's poor level (50% vs 0004's 45%, both far below 0003's 70%) rather than recovering as the dilution-only theory predicted.
- **LIBERO-90 task 73 (book-in-caddy) swung across the full range with no design mechanism to explain it**: 0% (baseline) -> 40% (0003) -> 20% (0004) -> 100% (0005), even though none of these three experiments touched libero_90's own weight or any caddy-specific data.

**Conclusion**: single training runs (one seed each) evaluated at n=5 trials/task are not reliably separating true design effects from run-to-run noise once the effect sizes get into the 10-40 percentage-point range (as opposed to the unambiguous 0/5-vs-50/50-baseline collapses seen in 0001/0002, which remain trustworthy). Before running further single-shot weight-tuning iterations, consider: (a) increasing eval trial count on the cheap panel (e.g. 10-15/task) to tighten measurement noise; (b) a repeated-seed check (same recipe, different seed) to directly quantify training-run variance; (c) broader per-suite task coverage (not just 4 sentinel tasks) so a suite's true rate is less exposed to single-task noise. Do not treat the exp0004 "zero-sum dilution" narrative as confirmed going forward — it may be partially real but is not cleanly demonstrated by the evidence collected so far.

### Investigation: exp0001 suite-selective catastrophic forgetting (2026-08-08)

Symptom: exp0001 (joint fine-tune, 4-suite+LIBERO-90 mix, lr=3e-5, 4000 steps) showed severe forgetting on LIBERO-Goal and LIBERO-Long (collapsed to 0-20% from 94-100%) but Object was fine and Spatial only partially regressed, at the final (step 4000) checkpoint.

**Evidence gathered:**
1. Training loss (both `loss_video` and `loss_action`) decreased smoothly throughout with no divergence/instability — rules out an optimization pathology; this is a representational/data phenomenon.
2. Diagnostic eval of 6 sentinel tasks (goal 0&5, long 0&5, spatial 5, object 5) at intermediate checkpoints: **at step 1000 AND step 2000 (50% through training), ALL 6 are at 0/5 — including object task 5**, which fully recovered to 100% by step 4000. Object's recovery happened late (between step 2000-4000), not gradually from the start.
3. LIBERO-Goal has direct task-template overlap with many LIBERO-90 tasks: Goal task 7 "turn on the stove" is the *literal same instruction* as LIBERO-90 tasks 20 and 44; Goal's "open the middle drawer of the cabinet" / "put the bowl on the stove" / "put the bowl on the plate" closely mirror several LIBERO-90 drawer/stove/plate tasks with slightly different objects/positions. This is a plausible source of persistent interference specific to Goal (conflicting/diluted supervision for near-identical instructions).
4. LIBERO-Long is 100% multi-step/long-horizon tasks (e.g. "put both X and Y in basket") while every added LIBERO-90 task is single-step. LIBERO-90 also outnumbers Long by ~10:1 in episodes (3921 vs 388). Plausible mechanism: the mix biases the model toward single-step/early-termination behavior, structurally hurting Long specifically, not just diluting it.
5. Per-suite episode counts in the new 5-dataset mix: spatial 434, object 457, goal 433, long 388, libero_90 3921 (combined 5633) — object has the most original-suite episodes, long the fewest, consistent with (but not sufficient to fully explain, since goal≈spatial in count yet goal fared much worse) the recovery-robustness ordering observed.

**Leading explanation**: a "stability gap" (documented continual-learning phenomenon) — introducing a large new data distribution causes an immediate, broad collapse across old tasks that *selectively* recovers as training continues; some suites (object) complete this recovery within the given budget, others (goal, long, and partially spatial) do not, plausibly due to genuine structural obstacles (goal's template overlap; long's single-step bias and low episode count) rather than just needing more time — though "just needs more time" (simple duration insufficiency) has not been ruled out and is the cheapest hypothesis to test first, since it requires no redesign, only resuming the existing step_004000 full-state checkpoint for more steps.

**Next candidate (0002)**: extend training from exp0001's step_004000 state checkpoint (full accelerate/deepspeed state, kept on disk) for additional steps, with progress checks on the widened 21-task cheap panel at intervals, to test whether goal/long/spatial recover like object did given more time. If this does NOT resolve goal/long, the next things to try are a reweighted data mix (protect original suites' effective gradient share, directly targeting the dilution/interference hypothesis) and/or Long-specific oversampling.

### Literature scan for LIBERO-90 candidate design (2026-08-08, while baseline eval was running)
- Recent VLA/robot-policy continual-learning literature (e.g. "Simple Recipe: VLA Models as Continual Learners", arXiv:2603.11653) reports that simple sequential/joint fine-tuning with LoRA and a large pretrained backbone achieves near-perfect retention (~98%) on prior tasks, often matching or beating more complex continual-learning methods (replay/regularization/architectural). Relevant caveat: FastWAM currently has **no LoRA/adapter support** in the codebase (confirmed earlier — only `model.dit` full fine-tune, VAE/text-encoder frozen), so the retention benefit those papers attribute partly to LoRA's implicit regularization may not transfer directly to a full-fine-tune-only setup; low LR / short fine-tune duration / joint (not purely sequential) data mixing are the more directly applicable levers here.
- Other retention-focused ideas surfaced (not yet assessed for applicability to FastWAM's specific WAM/action-diffusion architecture): trajectory-level reward shaping for RL fine-tuning (RaPO), skill-library/replay approaches (LOTUS), latent-consistency distillation (M2Distill). These assume an RL or skill-discovery framing FastWAM doesn't currently have — worth revisiting only if simple joint SFT fine-tuning underperforms on retention.

### Diagnostic: `libero_goal` task 0 ("open the middle drawer of the cabinet") — persistent 0% collapse, root cause hypothesis (2026-08-09, done while exp0006 training occupied all 4 GPUs)

Symptom noted in `STATE.md`: this task is 0/5 in every reweighted experiment (0003, 0004, 0005) regardless of goal/long weight — the one fully stable negative signal amid the otherwise-noisy 0003->0005 comparisons.

**Evidence gathered (no GPU needed — reused existing eval result JSONs + benchmark registry inspection):**
1. Task-0 success across runs (raw counts, not rates — panel is 5 trials except baseline's 50): baseline_0000 (zero-shot, pre-any-LIBERO-90-training) = **50/50 (100%)**; exp0001 (first joint LIBERO-90 mix) = 1/5 (20%); exp0003/0004/0005 (all reweighted mixes) = 0/5 (0%). So this is not a pre-existing weakness — the *unmodified released checkpoint solves this task perfectly*. Every LIBERO-90-joint-training run destroys it, and the destruction gets total (100%->20%->0%) as LIBERO-90/reweighting exposure increases.
2. Inspected `libero_90`'s benchmark registry for drawer-related tasks: LIBERO-90's kitchen scenes (`KITCHEN_SCENE1/4/5/10`) contain many "open/close the **top** drawer" and "open/close the **bottom** drawer" tasks (at least 9 distinct top/bottom-drawer task variants), but **zero tasks anywhere in LIBERO-90 mention a "middle" drawer** — the LIBERO-90 kitchen cabinets are 2-drawer (top/bottom) fixtures, while `libero_goal` task 0's cabinet is a 3-drawer fixture with a middle drawer.
3. This is a clean interference mechanism, not just template overlap: LIBERO-90 (oversampled up to 10x in some runs) massively over-represents "open the top/bottom drawer" instruction-to-motor-primitive mappings on visually similar cabinet fixtures, while "middle" as a drawer-position token becomes comparatively rare/novel. Plausible failure mode is the policy defaulting to the dominant top/bottom drawer-opening primitive (or the nearest-trained cabinet position) regardless of the "middle" instruction — an instruction-conditioning override, not a generic capability loss (the model clearly still knows how to open *a* drawer).

**Leading explanation**: task-level lexical/visual collision between a rare instruction token ("middle") and a heavily-oversampled near-duplicate scene category (top/bottom drawer opening), amplified by LIBERO-90 oversampling weight. This is a specific, falsifiable instance of the general "reweighting one suite dilutes/distorts unrelated near-duplicate instructions" risk — worth keeping in mind for any future candidate that increases LIBERO-90 weight further without addressing instruction-conditioning robustness.

**Not yet tested**: whether this is fixable by (a) reducing LIBERO-90 weight, (b) explicit rehearsal/oversampling of `libero_goal` task 0 specifically, or (c) is a structural language-conditioning weakness independent of mix weight (would need a targeted diagnostic eval — e.g. does the model open *some* drawer on this instruction, or fail the whole manipulation? — by inspecting rollout videos/logs, which the raw JSONs alone don't show). Worth a cheap targeted diagnostic (single task, few trials, existing checkpoint) once GPUs free up, before spending a full candidate experiment on it.

**Update (2026-08-10, exp0009)**: after doubling training to 8000 steps (fresh run, same recipe), this task moved from 0/5 to **2/5 (40%)** — the first non-zero result across five separate reweighted runs (0003, 0004, 0005, 0006, and 8000 steps of 0009's own predecessor recipe). This softens the "purely structural, unrecoverable by more of the same training" framing — sufficient additional training exposure appears to partially overcome the interference, though the task is still far from reliably solved. Worth re-checking again at exp0010's step 12000 to see if the trend continues.

### CRITICAL: resume-from-state-directory + `max_steps` extension is broken (LR re-warmup bug) (2026-08-10)

**Superseded/broadened by the finding below** ("resuming training from ANY of this project's own saved checkpoints catastrophically corrupts task performance") — this LR-schedule bug is real and independently confirmed, but experiment 0008 showed it is not the sole or even primary cause of the collapse; read that entry for the full picture before deciding how to handle any future resume-based training plan.

**Do not use `resume=<checkpoints/state/step_XXXX directory>` combined with a higher `max_steps` override to "extend" a training run — it silently re-warms the learning rate from near-zero back up to the original peak instead of continuing the decay, and will wreck an already-converged checkpoint.**

Discovered via experiment 0007 (extending exp0006's reweighted-recipe checkpoint from step 4000 to step 8000 by resuming its full accelerate/deepspeed state directory). Result: total catastrophic collapse across every suite (overall cheap-panel score 59.6% -> 10.8%, e.g. Object 95%->10%, Spatial 70%->5%) — far beyond the ~20pp/suite noise floor separately established in experiment 0006. Root cause, confirmed by extracting the `lr=` value from the training log across the full extension:

```
step=4010  lr=3.01e-07   (effectively a fresh warmup start, right after resume)
step=5010  lr=5.18e-06
step=6010  lr=1.65e-05
step=7010  lr=2.69e-05
step=7710  lr=3.00e-05   (= the ORIGINAL peak LR of the first 4000-step run)
step=7960  lr=2.99e-05   (still ~peak, barely starting to decay in the last ~150 steps)
```

Mechanism: `Wan22Trainer.__init__` (`src/fastwam/trainer.py`) always constructs a **fresh** warmup+cosine `SequentialLR` sized for the current `self.max_steps` (the new override, e.g. 8000), regardless of the `global_step` a resumed checkpoint will restore. When `accelerator.load_state()` later restores the old scheduler's internal counter into this differently-shaped new scheduler object, the net effect is that nearly the entire extension window is spent ramping the LR from near-zero back up toward the new schedule's peak, rather than continuing the original decay from wherever it left off. A model that had already converged to a low-LR optimum gets dragged back through a near-full-strength re-warmup, destroying the converged weights.

This same pattern (`resume=<state dir>`, `max_steps=<new total>`) was also used by **experiment 0002** to extend experiment 0001's training — that experiment's "extending training helped object recover" conclusion should be treated with new skepticism; it was not re-verified as part of this finding, but the same bug mechanism plausibly applied there too, and any future decision that depends on exp0002's specific conclusion should be re-examined via a corrected extension or a fresh run.

**Workaround used going forward (validated safe)**: resume from the **weights-only `.pt` checkpoint** instead of the full-state directory (`resume=<checkpoints/weights/step_XXXX.pt>`), which is the exact same clean mechanism already used successfully by every other experiment in this project (0001, 0003, 0004, 0005, 0006, all resuming from the released checkpoint's weights). This discards the optimizer momentum/variance state and starts a fresh, correctly-shaped schedule (own warmup + cosine decay) for the new run's own `max_steps` budget — not a mathematically pure continuation, but far safer than the broken directory-resume path, and consistent with how every validated experiment in this project has actually launched training. Used for experiment 0008 (continuing exp0006's checkpoint at a lower `lr=1e-5` for `max_steps=2000`).

**Proper fix, not yet implemented**: `_build_scheduler` should be called with `total_train_steps = max_steps - global_step_at_resume` and `warmup_steps=0` (or a small fraction of the *remaining* budget) whenever a directory-resume restores a nonzero `global_step`, so the schedule picks up decaying from the current LR rather than restarting warmup. Do not attempt directory-resume-based extension again until this is fixed and verified with a short smoke test.

### CRITICAL: resuming training from ANY of this project's own saved checkpoints catastrophically corrupts task performance — root cause not fully pinned down, workaround is "always resume from the originally-released checkpoint only" (2026-08-10)

**Do not launch training with `resume=` pointing at any checkpoint produced by this project's own training runs (weights-only `.pt` or full-state directory). Only `resume=checkpoints/fastwam_release/libero_uncond_2cam224.pt` (the originally-released checkpoint) is currently safe.**

This supersedes and broadens the earlier "LR re-warmup bug" note below — that bug is real and still worth fixing, but it is **not** the (sole) explanation for the catastrophic collapses seen in experiments 0007 and 0008. Full investigation:

1. **exp0007** (directory-state resume of exp0006 + `max_steps` override, 4000->8000 steps): collapsed from 59.6% to 10.8% overall on the cheap panel. Root-caused at the time to a broken LR schedule (re-warmed from near-zero back to the original peak `3e-5`).
2. **exp0008** (weights-only resume of exp0006 + a fresh, correctly-shaped schedule at `lr=1e-5`, `max_steps=2000`): collapsed even further, to 3.0% overall — **despite a verified-correct, properly-decaying LR schedule** (confirmed via the log's `lr=` trace ending at `1.00e-07`). This ruled out the LR-schedule bug as the full explanation, since a demonstrably correct schedule produced an equally catastrophic result.
3. **Targeted diagnostic**: resumed exp0006's step_004000.pt weights-only into a fresh trainer and ran exactly **1 training step** at `lr≈1e-7` (i.e., essentially zero real optimization — a pure reload+immediate-resave test), then evaluated the resulting checkpoint on 4 tasks that scored 100% in exp0006's own original eval (`libero_object` 3/5/8, `libero_90` task 24). **Result: 0/5 on all 4 tasks** — total failure with virtually no training having occurred. This proves the corruption happens in the checkpoint **save/load/model-construction roundtrip itself**, not from any meaningful amount of optimization.
4. **Ruled out eval-config artifacts**: re-evaluated the same 1-step-diagnostic checkpoint using the exact task config that exp0006 itself used for its own (successful) eval, instead of a newly-created config — still 0/5 on all 4 tasks. This rules out a Hydra config-composition issue specific to the newly-created task configs as the explanation.
5. **Ruled out gross checkpoint-file corruption**: directly loaded and compared `mot.state_dict()` between the released checkpoint, exp0006's step_004000.pt, and the 1-step diagnostic checkpoint. All three have **identical key sets** (1649/1649 keys, zero missing/extra on either side) and the action_encoder/head/video-head tensors sampled from all three have statistically normal, comparable magnitude (mean/std in the same range, no NaN/Inf). So the corruption is not a gross key-mismatch or an obviously-zeroed/randomized parameter, at least not in the specific tensors sampled.

**What is known**: training's model construction (`configs/model/fastwam.yaml`: `skip_dit_load_from_pretrain: false`, `action_dit_pretrained_path: <ActionDiT backbone file>`) always loads a generic pretrained ActionDiT backbone first — which explicitly logs `random_kept_prefixes=['action_encoder.', 'head.']`, meaning those specific submodules are randomly initialized at this construction step — and only *afterward* applies `resume=<checkpoint>` via `mot.load_state_dict(payload["mot"], strict=False)`. Eval's model construction (`configs/sim_libero.yaml`: `skip_dit_load_from_pretrain: true`, `action_dit_pretrained_path: null`) skips this step entirely and loads the checkpoint directly into a blank shell. This asymmetry is a real, confirmed difference between the two code paths, and is the most likely location of the bug, but the exact mechanism (why `strict=False` doesn't fully restore the checkpoint's actual trained values despite matching key names) was not pinned down further given the compute cost of continued investigation — this would need e.g. a full numerical diff of all 1649 tensors (not just 3 samples) between a checkpoint before/after going through the training-construction-and-resave path, or instrumenting `load_state_dict`'s actual `missing_keys`/`unexpected_keys` return value at resume time (currently discarded, not logged) to see if there ARE silently-dropped keys the simple set-comparison above missed (e.g. if `strict=False` reports keys as "loaded" by name but with a shape mismatch that gets silently skipped rather than erroring).

**Practical impact — this materially limits available candidate designs going forward**: any research idea that depends on "continue training from a promising intermediate/final checkpoint" (extending a run, further fine-tuning a good checkpoint at a different LR, curriculum approaches that stage from an earlier checkpoint, etc.) is **not currently usable** until this bug is fixed. Every future candidate must launch a **fresh single continuous run** with `resume=checkpoints/fastwam_release/libero_uncond_2cam224.pt` from the start, even if that means repeating compute a related earlier experiment already spent (as done for experiment 0009, which retests "does more training help the reweighted recipe" via a fresh single 8000-step run from the released checkpoint rather than resuming exp0006's 4000-step checkpoint).

**Recommended follow-up if this becomes a priority**: instrument `FastWAM.load_checkpoint`'s `strict=False` call to capture and log `missing_keys`/`unexpected_keys`/any shape-mismatch warnings explicitly (PyTorch's `load_state_dict` returns this info but the current code discards it), and compare behavior when resuming from the released checkpoint (known-good) vs. one of our own saved checkpoints (known-broken) with otherwise identical code — the difference in what does/doesn't load should immediately localize the bug.

### FIX IMPLEMENTED AND VALIDATED (2026-08-10) — resuming from our own checkpoints is now safe

**The standing constraint above is lifted for weights-only resumes.** Root cause: `_resume_or_load_checkpoint()` (`trainer.py`) called `accelerator.unwrap_model(self.model).load_checkpoint(...)` **after** `accelerator.prepare()` had already wrapped the model in DeepSpeed ZeRO. DeepSpeed's mixed-precision optimizer keeps its own FP32 "master" parameter copies separate from the BF16 "working" copies used in forward/backward; loading weights into the unwrapped module post-wrap only updates the BF16 working copy in place. The moment the first optimizer step runs, DeepSpeed resyncs the BF16 working copy from the (still pre-resume, randomly-initialized) FP32 master — silently discarding the resumed values for any parameter whose master wasn't otherwise touched. `action_encoder`/`head` were the visible casualties because they're the only submodules that start from a genuinely random init at construction time (`ACTION_BACKBONE_SKIP_PREFIXES` in `action_dit.py`) rather than from a value close to the checkpoint's own (everything else starts "close enough" that the effect is masked).

**Fix**: for a weights-only `resume=` (a `.pt` file, not a full-state directory), load the checkpoint into the raw model **before** `accelerator.prepare()` wraps it, so DeepSpeed's FP32 master copies get initialized from the correct resumed values from the start. Implemented in `trainer.py` (commit `99826cc`): a new pre-wrap loading block right before the `accelerator.prepare()` call, plus a `self._weights_resumed_early` flag so `_resume_or_load_checkpoint()`'s existing post-wrap branch skips re-loading (it still handles the directory/full-state resume case unchanged, which legitimately needs to run after `prepare()` since it also restores optimizer/scheduler state).

**Validation (same cheap 1-step-diagnostic pattern used to find the bug)**: resumed exp0010's step_012000.pt checkpoint with the fix, ran exactly 1 training step (lr≈1e-7, i.e. negligible real training), then evaluated on the same 4-task panel (`libero_object` 3/5/8, `libero_90` task 24) that scored 0/20 (0%) with the old code. **Result: 20/20 (100%)** — exactly matching exp0010's own native performance on these tasks. Confirms the fix works and resuming from our own checkpoints is now safe for weights-only resumes.

**Practical implication**: future "does more training help" tests can now resume directly from a prior checkpoint (e.g. exp0010's step_012000.pt) instead of relaunching a full run from the released checkpoint every time — a large compute savings for iterative extension.

### SECOND FIX IMPLEMENTED (2026-08-10) — directory/full-state resume LR-schedule bug (from exp0007), not yet validated

The weights-only fix above does not address exp0007's separate LR-schedule bug for **directory/full-state resume** (`accelerator.load_state()`). Root cause, now precisely understood: `accelerator.load_state()` restores the scheduler's raw internal step counter from the checkpoint, but that counter is only meaningful if the schedule's shape (`total_train_steps`/`warmup_steps`, derived from `self.max_steps`) is unchanged from when it was saved. Extending `max_steps` (the whole point of a directory resume for "train longer") makes `__init__` build a *new* schedule shaped for the new total *before* `load_state()` runs — the counter that then gets restored belongs to the *old* shape and gets reinterpreted against the wrong boundaries, producing exp0007's observed nonsensical LR re-warmup.

**Fix implemented** (commit `b2b49d0`, `trainer.py`): added `_resync_scheduler_to_global_step()`, called after `accelerator.load_state()` in `load_training_state()` (both its normal and fallback branches). It rebuilds a scheduler in the *current* shape (using the possibly-just-overridden `self.max_steps`) and fast-forwards it via repeated `.step()` calls to `self.global_step`, then copies that corrected state into the real scheduler and pushes the resulting LR into the optimizer's param groups (since `load_state_dict()` alone doesn't touch the optimizer). This is deterministic and reproduces the same trajectory `accelerate` would have restored when `max_steps` is unchanged (a true no-op case), and is correct when it's extended.

**VALIDATED (2026-08-10)**: per explicit user instruction, exp0012 (the real continuation run, which used weights-only resume and was therefore not exercising this second fix) was stopped intentionally so this fix could be validated *before* any further real training — the user's reasoning: don't keep running training that doesn't test whether every resume path is actually fixed. Validation used exp0012's own partial full-state checkpoint (`step_000500`, saved at global_step=500 under a schedule shaped for `max_steps=4000`) as the resume source, with `max_steps` overridden to `8000` (a genuinely different shape — the exact scenario that broke exp0007) via a throwaway diagnostic task config (`libero_uncond_2cam224_plus90_reweighted_diag_dirresume.yaml`).

**Result: `Re-synchronized LR scheduler to global_step=500 (shape: total_train_steps=8000, warmup_steps=400); lr=2.9987e-05`** — global_step 500 is just past the new schedule's 400-step warmup, so a value near peak LR is exactly correct (barely past warmup in an 8000-step schedule). The next two logged training steps held `lr=3.00e-05` with no jump or discontinuity, and training losses (0.16-0.22) looked normal, not disrupted. This is a smooth, sane continuation — a world apart from exp0007's original symptom (LR silently reset to `~3e-7` right after resume, then slowly re-ramping to peak over thousands of steps).

**Both resume mechanisms are now confirmed fixed and safe to use**:
- Weights-only resume (`resume=<file.pt>`) — fixed by commit `99826cc`, validated via 1-step diagnostic (100% vs. 0% on a 4-task panel).
- Directory/full-state resume (`resume=<state_dir>`) — fixed by commit `b2b49d0`, validated via the LR-resync test above.

Choice between them is now a free design decision depending on the experiment: weights-only resume starts a fresh optimizer/schedule from the checkpoint's weights (useful when you want a different LR/schedule for the next phase, or don't need exact optimizer-momentum continuity); directory resume preserves the exact optimizer state and continues the LR schedule seamlessly (closer to "as if the original run had just kept going," useful for pure step-count extension with no other changes). Diagnostic artifacts (`exp_diag3_dirresume`, and exp0012's own stopped partial run) were deleted after validation — no further value beyond the finding recorded here.

**Lead investigated and ruled out (2026-08-10)**: the training log's line `"Loaded .pt weights only; optimizer/scheduler/step were not restored under ZeRO2"` (`trainer.py:278`) looked suspicious since the launch script is `train_zero1.sh` — raising a hypothesis that training might actually be running DeepSpeed ZeRO **stage 2** (which shards parameters, not just optimizer state) despite the script's name, and that `accelerator.unwrap_model(self.model).state_dict()` might be silently gathering sharded parameters incorrectly when saving. **Checked directly: `scripts/accelerate_configs/accelerate_zero1_ds.yaml` points at `scripts/ds_configs/ds_zero1_config.json`, which explicitly sets `"stage": 1`.** The "ZeRO2" wording in the log is simply a hardcoded, apparently-mislabeled literal string in `trainer.py` — not a dynamic check of the actual stage — so this is a red herring, not evidence.

**ROOT CAUSE FOUND (2026-08-10)**: ran a full numerical diff of all 1649 `mot.state_dict()` tensors between exp0006's checkpoint and the 1-step diagnostic checkpoint (parent -> 1-step-reload-and-resave). 1381 tensors changed only negligibly (consistent with 1 near-zero-LR optimization step) and 141 were bit-identical, but **exactly 3 tensors stood out with a relative difference of ~1.3 (far above every other tensor, which topped out around 0.9 and mostly sat under 0.4): `mixtures.action.head.weight`, `mixtures.action.action_encoder.bias`, `mixtures.action.action_encoder.weight`** — precisely the two submodules the model-construction log flags as `random_kept_prefixes=['action_encoder.', 'head.']`.

Cross-checked against exp0006's own training log (a normal, successful first-stage run resuming from the **released** checkpoint): `action_l2` starts at **0.087 at step 200** and decreases steadily to **0.015 by step 4000** — a clear from-scratch learning curve, not a flat "already good, minor fine-tuning" trajectory a correctly-loaded pretrained head would show.

**Conclusion: `action_encoder`/`head` are never correctly restored by `resume=` at all, for ANY checkpoint (released or our own).** They always start from the random initialization baked in during `create_fastwam`'s ActionDiT-backbone construction step, and `mot.load_state_dict(payload["mot"], strict=False)` does not actually overwrite them from the resumed checkpoint despite the checkpoint file itself containing correct, matching-key-name, well-trained values for those tensors (independently confirmed clean via a full 1649-tensor diff against the released checkpoint — zero anomalies). Every prior "successful" experiment (0001, 0003, 0004, 0005, 0006, 0009, 0010) was not actually loading a pretrained action head at all — it was **relearning a fresh one from scratch** over its own full training budget, at a properly warmed-up-to-peak LR (3e-5, 4000+ steps) — comfortably enough for a small (1024x7) linear projection to converge, so nobody noticed. The three broken "continuation" runs failed specifically because they didn't have comparable effective high-LR training time to redo that relearning: exp0007's broken schedule wasted most of its 4000 steps ramping LR from near-zero back to peak; exp0008 had only 2000 steps at a much lower peak LR (1e-5); the 1-step diagnostic had essentially none. This is a complete, well-evidenced explanation, not just a workaround — the earlier framing ("resuming from our own checkpoints is unsafe") is correct as an operational rule but the actual mechanism is "the action head is silently never restored by resume, and short/gentle continuations don't get enough budget to compensate," which applies identically regardless of which checkpoint is being resumed.

**Implication for future work**: the standing constraint (only `resume=checkpoints/fastwam_release/libero_uncond_2cam224.pt`, full first-stage-length runs) remains the correct practical guidance, since it's what's been empirically validated — but the reason is now understood: any future "continue training" attempt would need either (a) a proper fix so `resume=` actually restores `action_encoder`/`head`, or (b) a training budget/LR schedule generous enough to relearn that layer from scratch, which defeats most of the purpose of a cheap continuation. Fixing (a) directly (e.g., checking why `strict=False` doesn't apply these specific keys — possibly a key-name mismatch specific to how the ActionDiT-backbone-construction step names them vs. how they're saved, since the checkpoint file's key names were confirmed identical to the released checkpoint's) would be the highest-value follow-up if extending training cheaply becomes a priority again.

### New technique: task-level oversampling via a filtered LeRobot dataset subset (2026-08-12, exp0017)

`RobotVideoDataset`/`BaseLerobotDataset` (`src/fastwam/datasets/lerobot/`) has no built-in per-task or per-episode filtering/weighting — `dataset_dirs` is a flat list of whole-suite LeRobot-format directories, oversampled only by listing a directory multiple times (the existing goal5x/long5x mechanism). To oversample specific *tasks within* a suite (not the whole suite), built a standalone filtered LeRobot dataset directory:

1. Read the source suite's `meta/episodes.jsonl` (maps `episode_index` -> task instruction text + length) and `meta/episodes_stats.jsonl` (per-episode normalization stats — unaffected by subsetting, just copy the matching entries).
2. Filter to episodes whose instruction text exactly matches the target task description(s). **Caveat discovered**: LIBERO-90 reuses identical instruction text across multiple distinct numeric task_ids in different scenes (e.g. eval task73 and task81 are both "pick up the book and place it in the front compartment of the caddy" — confirmed via `info.json`'s `total_tasks: 73` vs LIBERO-90's 90 nominal task_ids). Since the model only ever sees instruction text (not the eval harness's numeric task_id), text-matching is actually the *correct* granularity for this purpose, not a limitation.
3. Symlink (not copy) each selected episode's `data/chunk-XXX/episode_NNNNNN.parquet` and `videos/chunk-XXX/{video_key}/episode_NNNNNN.mp4` into a fresh directory under a renumbered, contiguous `chunk-000` (the loader's `LeRobotDatasetMetadata` requires contiguous `0..total_episodes-1` indexing — sparse/gapped indices don't work). Symlinks are sufficient; the dataset loader reads through them transparently (verified) and it avoids duplicating GBs of video data.
4. Write matching `meta/episodes.jsonl` (renumbered), `meta/episodes_stats.jsonl` (renumbered, stats copied verbatim), `meta/tasks.jsonl` (fresh `task_index` for just the included task strings), and `meta/info.json` (updated `total_episodes`/`total_frames`/`total_videos`/`total_tasks`/`total_chunks`/`splits`).
5. Add the new directory to a `dataset_dirs` list (repeated N times for oversampling) like any other suite directory — no code changes needed downstream.

Verified end-to-end (not just spot-checked) via a direct `BaseLerobotDataset` instantiation + `dataset[0]` call before spending any GPU time — this is a cheap, reliable pre-launch smoke test for this kind of data-engineering change and should be repeated for any future filtered-subset dataset. Also verified `task 51` ("pick up the butter and put it in the basket", LIBERO-90's single weakest task at 38% canonical) has **zero exact-matching training demonstrations** in the source data — confirms it's a genuine data gap (excluded from the oversampling target; would need new data collection/synthesis, not a training-recipe fix) rather than assuming oversampling would help every weak task equally.

### Infra bug: repeated `SIGKILL`-based cleanup between failed launch attempts left orphaned processes that caused a cascade of misleading dataset/directory errors (2026-08-12/13, exp0017)

Launching exp0017 (the LIBERO-90 weak-task-oversampling candidate, see `PROGRESS_0017`) crashed repeatedly with `ValueError: <N> is not in list` inside the vendored `lerobot_dataset.py`'s multi-dataset `__getitem__` (`self.episodes.index(ep_idx)` failing for an `ep_idx` that should have been valid for that sub-dataset). Extensive investigation chased this as a suspected deep, pre-existing bug in the vendored LeRobot multi-dataset code: verified the new filtered subset dataset was correctly built (fixed parquet `episode_index`/`index`/`task_index` columns after an initial real bug there — see the "task-level oversampling" note above), verified via a full `accelerate launch --num_processes 4` dry run that dataset construction succeeds cleanly across all 4 ranks, and still saw the same error class recur in real training launches — including, once, alongside a `RuntimeError: Parent directory .../checkpoints/weights does not exist` at a checkpoint save, even though `ensure_dir()` (plain `os.makedirs(path, exist_ok=True)`, called unconditionally at trainer construction) should make that impossible.

**Root cause**: across ~7 failed launch attempts, failed jobs were killed with `kill -9` / `pkill -9` on the wrapper script and `accelerate launch` process. `SIGKILL` does not allow `torchrun`'s elastic launch agent to cleanly terminate/reap its own child worker processes, so it is plausible (and consistent with log evidence — e.g. a crash trace referencing an `output_dir` timestamp nearly an hour older than the attempt believed to be running) that **orphaned worker processes from earlier killed attempts kept running in the background**, concurrently reading/writing the same output directories and the same shared HuggingFace `datasets` parquet cache (`/workspace/.hf_home/datasets/parquet/`) that the new attempt was also using — corrupting shared state and producing exactly this class of "impossible" index/directory errors.

**Fix**: before any relaunch after a failure, explicitly verify a **fully clean state** — not just that the last known PID is gone, but `ps aux | grep -E "train.py|accelerate|torchrun"` returns nothing at all, and `nvidia-smi` shows 0MB used on every GPU. Once verified clean, a fresh launch (same exact config that had failed repeatedly) ran to completion with zero errors. **Operational lesson**: `kill -9` is a last resort for wedged distributed-training processes specifically because it can leave the process *group* half-alive; prefer a graceful `kill` (SIGTERM) first when the process is responsive, and always explicitly verify full cleanup (all matching process names gone, all GPU memory freed) before relaunching — never trust "my tracked PID is gone" alone for a multi-process distributed launcher.
