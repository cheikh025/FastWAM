**FIX CONFIRMED WORKING (2026-08-10)**: the `resume=` checkpoint-corruption bug is fixed for weights-only resumes. Root cause: `_resume_or_load_checkpoint()` loaded weights into the model AFTER `accelerator.prepare()` wrapped it in DeepSpeed, so the FP32 mixed-precision master parameter copies stayed at their pre-resume (random) values; the first optimizer step overwrote the freshly-loaded BF16 working weights from that stale master, silently erasing the resume for `action_encoder`/`head`. Fix (commit `99826cc`): load weights-only resume checkpoints into the raw model *before* `accelerator.prepare()`. Validated via the same cheap 1-step-diagnostic pattern: a 1-step reload of exp0010's checkpoint with the fix scored **100%** on a 4-task panel that scored 0% with the old code. **exp0011 (a fresh 16000-step restart) was stopped intentionally by explicit user instruction** once this investigation began, on the reasoning that repeating full restarts is wasteful now that a real fix is achievable — this is now validated as the right call.

**MAJOR INFRA FINDING, root cause fully identified (2026-08-10)**: `resume=` never actually restores the `action_encoder`/`head` submodules for ANY checkpoint — released or our own. A full 1649-tensor numerical diff between a checkpoint and its 1-step reload/resave showed only `mixtures.action.action_encoder.{weight,bias}` and `mixtures.action.head.weight` changed drastically (rel. diff ~1.3 vs <0.9 for everything else) — exactly the submodules training's model construction randomly initializes (`random_kept_prefixes=['action_encoder.', 'head.']`) before `resume=` is applied via `strict=False`, which silently fails to overwrite them despite the checkpoint file containing correct, matching-key-name values (confirmed clean via a full tensor diff against the released checkpoint — zero anomalies). Cross-checked against exp0006's own training log: `action_l2` starts at 0.087 (step 200) and falls to 0.015 (step 4000) — a from-scratch learning curve. **Every prior successful experiment was silently relearning the action head from scratch over its own full training budget at a properly warmed-up-to-peak LR; the broken continuations (exp0007's mis-scheduled LR, exp0008's short low-LR budget, the 1-step diagnostic) simply didn't have enough effective high-LR time to redo that relearning.** A ZeRO-stage-mismatch theory was also investigated and ruled out (confirmed `ds_zero1_config.json` genuinely sets `stage: 1`; the log's "ZeRO2" wording is just a mislabeled hardcoded string). **Practical constraint unchanged: every future candidate must `resume=checkpoints/fastwam_release/libero_uncond_2cam224.pt` only, as a full first-stage-length run** — until `resume=` is fixed to actually restore the action head, any "continue training" attempt either needs this same full-length budget (defeating the point of a cheap continuation) or will silently fail.
